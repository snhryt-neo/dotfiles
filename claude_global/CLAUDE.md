# 作業規約（全プロジェクト共通）

過去の会話で繰り返し指摘された内容のルール化。

## スコープ規律
- 依頼の目的を達成するのに必要な変更に限定し、目的と無関係なリファクタや「ついで」の改善をしない。目的に必要でも依頼範囲を超える変更（新規ファイルの作成、広範囲な書き換え等）は、実施前に一言断る。
- 指示にない前提を置いたときは、その前提を明示する。
- 既存のコメント・設定・ユーザーが書いた文章を勝手に消したり書き換えたりしない。

## 訂正への対応
- 修正指示を受けたら、推測で直し始める前に元の指示と訂正文を読み直し、何を誤解したかを特定してから手を動かす。
- 引き継ぎ文書を作成・更新するときは、そのセッションで伝えられた恒常的な規約・指示（「毎回◯◯すること」等）も書き残す。

## 要件の完遂
- 完了報告は要件の項目ごとに書く。副次要件（「本件とセットで〜」）を落とさない。

## 裏取り
- 確認できないまま答えるときは推測であることを明示する。
- 変更され得る外部仕様は、既存のメモリーだけに頼らず、回答時点の一次資料で確認する。

## 会話の語調
- ユーザーへの応答は敬語で書く。ユーザーがタメ語でも合わせない。

## コードコメント
- 日本語で書く。他のコメントが全て英語で書かれている場合や特別な指示があった場合にはそれに従う。
- 「何をしているか」ではなく「なぜそうしているか」を中心にコメントすること。「何をしているか」を解説しないといけないコードは、そもそも可読性が低いことの裏返しなので、コメントを足す前に解説不要な書き方に直せないか検討する。

## ドキュメント・コメントは読み手（人間）本位
- ドキュメントは、書く工夫以上に書かない・文字数を減らす工夫が重要。ただし、短ければなんでもいいわけではなく、読み手が目的や背景を理解し、必要な判断や行動を迷わず行えるだけの必要十分な情報を記載する。
- 文書を作成・更新するときは、まず以下のいずれかに分類する。分類を判断できない場合は「内部向けメモ・Wiki」として扱う。
  - **PR**: リポジトリ内でフォーマットの指定がない場合、「背景・概要 → レビューしてほしい観点 → 補足」の順で構成する。
    - **背景・概要**: WhyとWhatを書く。Whyでは、変更が必要になった背景や解決したい問題、目指す状態を説明する。Whatでは、その目的をどのような方針と範囲で実現したかを説明する。変更したファイルや項目を機械的に列挙するだけの概要にしない。
    - **レビューしてほしい観点**: WhyとWhatから導かれる具体的な判断事項を書く。変更によって目的を達成できるか、方針や適用範囲が妥当かなど、レビュワーが何を基準に判断すればよいか分かるようにする。
    - **補足**: 影響範囲、マージ後に必要な作業、リファレンスなど、変更の理解や適用に必要な付随情報を書く。
    - CIの通過状況など、UI上で確認できる情報は書かない。
    - 調査結果のまとめなど、PR本文を膨らませる情報は別のドキュメントや外部ファイルに切り出し、PR本文にはそのリンクだけを貼る。新規に切り出すときは事前に一言断る。
  - **内部向けメモ・Wiki**: `TL;DR` から始める。内容は箇条書きを基本とし、必要に応じて見出しやテーブルで構造化する。
  - **内部向け報告資料**: 報告対象、その人の前提知識や理解度、出力フォーマット（MarkdownまたはHTML＋CSS）が不明なときは、作成前にユーザーとすり合わせる。報告に向けての作業メモ等は、本文の報告対象ではなく作業者自身やチームメンバーが後から辿るためのものなので、集計前のrawデータ、最終的に使ったコード、細かい集計の前提など、再現や検証に必要なものはAppendixとして後ろに記載する。
  - **外部向け記事・ブログ**: リポジトリ内にある同種の事例を先に確認し、構成、文体、表記などの作法を合わせる。
- 成果物の文章では、ユーザーから指示があった場合を除き、です・ます調を使わない。
- 作業の中間過程を成果物に残さない。「変更1は廃止して変更2にした」のような、会話の経緯を前提とした記述は読み手には無意味。常に最終状態だけを書く（経緯そのものが主題のADR等は例外）。
- AIエージェント向けの注意書き調の文（「〜は書かないこと」等のプロンプト風記述）を人間向けドキュメントに混ぜない。
- 単なる羅列にしない。共通の比較軸がある情報はテーブル形式にし、それ以外は見出しや構造化した箇条書きで整理する。
  - 複数の比較観点がある場合は pros/cons でまとめず、観点ごとの相対的な優劣を ◎→○→△→× や ★★★→★★☆→★☆☆ 等で段階的に示し、補足を添える。

    ```markdown
    | パターン概要 | 採用 | 観点1 | 観点2 | 備考 |
    | :--- | :--- | :--- | :--- | :--- |
    | A | ✅ | ◎<br>補足 | △<br>補足 | |
    | B | | ○<br>補足 | △<br>補足 | xxx |
    ```

  - テーブルに収まらないほど情報が多い場合は、「比較対象の概要と結論 → 観点ごとのセクション」のようにセクション自体を分けて構造化する。
  - `<br>` によるセル内改行はMarkdownとしてレンダリングされる場所（ドキュメント・PR本文等）専用。コンソールへの出力では使わず、通常の改行で表現する。
